기업 서비스 사용자 리뷰 기반 문제 분석

4비트 양자화 LLM과 few-shot 프롬프트로 사용자 리뷰를 구조화한 탐색적 분석

자연어 리뷰를 범주형 데이터로 변환해, 반복되는 앱 사용 불편을 탐색했습니다.

항목 내용
활동·기간 AI POC 클리닉 · 2026.08.05–2026.09.11
팀·역할 3명 · 데이터 분석 담당
데이터 Google Play Store 리뷰 500개 중 별점 1–2점 리뷰 350개
기술 Python, Pandas, PyTorch, Transformers, bitsandbytes
모델·환경 Qwen2.5-7B-Instruct · NF4 4비트 양자화 · Google Colab

문제 — 사용자 불편을 어떻게 분석 가능한 데이터로 바꿀까?

AI 서비스 기획 경험을 계기로 기업의 문제를 데이터로 탐색하는 데 관심을 갖고 POC 클리닉에 참여했습니다. 알라딘을 조사하면서, 앱 사용자가 보고하는 불편을 구체적인 근거로 정리하고자 했습니다.

리뷰는 사용자 경험을 살펴볼 수 있는 자료지만, 같은 문제도 다양한 표현으로 나타나고 여러 불편이 한 문장에 섞여 있습니다. 이에 LLM으로 리뷰를 사전 정의 범주에 분류하고, 비교·집계 가능한 형태로 구조화했습니다. 분석 범위는 리뷰에서 관찰 가능한 앱 사용 경험이며, 브랜드 문제 전체의 검증은 아닙니다.

접근 — 리뷰 수집부터 구조화까지

  1. 수집·선별: 한국어·한국 지역의 관련도 순 리뷰 500개를 수집하고, 별점 1–2점 리뷰 350개를 선정했습니다.
  2. 분류 기준 설계: 검색·탐색, 화면 구성·가독성, 버튼 반응·상호작용 인지, 장바구니·구매 흐름의 네 UI/UX 범주와 비UI/UX 범주를 사용했습니다.
  3. 리뷰별 추론: Transformers로 Qwen을 직접 로드하고, 영어 지시문과 few-shot 예시에 한국어 리뷰를 입력했습니다. 별도 학습이나 외부 LLM API 호출은 없습니다.
  4. 결과 저장·집계: UI/UX 여부, 단일 토픽, 분류 이유를 JSON으로 받아 원문·별점과 함께 저장하고 범주별 리뷰 수를 집계했습니다.

시행착오 — 모델 품질과 실행 환경의 제약

  • 소형 모델의 불안정한 응답 → 7B 모델 선택: 초기 소형 Qwen 모델에서 리뷰와 맞지 않는 응답과 환각을 경험해 더 큰 모델을 시도했습니다.
  • GPU 메모리 부족 → 4비트 양자화: 당시 Colab 환경에서 7B 모델이 로드되지 않아 NF4 4비트 양자화를 적용했고, 모델을 로드해 추론을 실행했습니다.
  • 한국어 출력의 중국어 전환 → 영어 지시문·JSON 출력: 한국어 리뷰는 유지하되 지시문과 출력 언어를 영어로 조정했습니다. 출력 언어 문제의 원인을 양자화로 확정한 것은 아닙니다.
  • 분류 기준 전달 → few-shot 예시: 리뷰와 기대 응답을 함께 제시해 범주 경계와 출력 형식을 구체화했습니다. 예시 추가의 효과를 정량적으로 비교한 실험은 수행하지 않았습니다.

위 내용은 진행 중 경험한 시행착오이며, 모델 간 성능을 측정한 벤치마크는 아닙니다.

결과 — 반복되는 불편을 후속 검토 대상으로 구체화

1. UI/UX 분류 리뷰의 74.8%가 버튼 반응·검색/탐색에 집중

부정적 리뷰 350개 중 111개(31.7%)가 UI/UX 관련으로 분류되었습니다. 이 중 버튼 반응·상호작용 인지 46개, 검색·탐색 37개로, 두 범주가 UI/UX 분류 리뷰의 74.8%(83/111개)를 차지했습니다.

이 표본에서는 화면 구성보다 사용자가 행동을 수행하고 원하는 항목을 찾는 과정에 관한 불편이 상대적으로 많이 분류되었습니다. 31.7%는 선정한 부정적 리뷰 내 비중이며, 전체 사용자의 불편 비율이 아닙니다. 그림의 ‘UI/UX 원인’도 원인 입증이 아니라 LLM 분류 결과를 의미합니다.

2. 버튼 반응·검색/탐색을 우선 검토 후보로 선정

버튼 반응과 검색·탐색은 리뷰 수가 많으면서 범주 내 1점 비율도 각각 87.0%(40/46개), 86.5%(32/37개)로 높았습니다. 이를 근거로 버튼·메뉴 반응과 탐색 동선을 원문 검토 및 사용성 테스트의 우선 후보로 정리했습니다.

그림의 ‘심각도’는 별도 평가 점수가 아닌 범주 내 1점 리뷰 비율입니다. 낮은 별점의 원인을 입증하거나 실제 개선 우선순위를 확정한 결과는 아닙니다.

나의 기여

데이터 분석 담당으로 데이터 출처 선정과 리뷰 수집·선별, LLM 기반 구조화 파이프라인 구성, 결과·분류 이유 저장, 범주별 집계 및 분석 근거 정리를 수행했습니다.

한계와 배운 점

  • 대표성: 관련도 순으로 수집한 낮은 별점 리뷰에 한정되어 전체 사용자로 일반화할 수 없습니다.
  • 분류 검증: 원문과 결과를 대조했으나 정답 데이터셋 기반 정확도 평가는 없습니다. 단일 범주 분류로 복합적인 불편이 축약될 수 있습니다.
  • 구현 한계: 원본 코드는 JSON 파싱 실패를 비UI/UX로 처리해 집계에 영향을 줄 수 있습니다. 실패 분리·재시도와 라벨 검증이 후속 과제입니다.
  • 성과 범위: 탐색적 분석 및 POC용 근거 마련이며, 실제 서비스 적용이나 개선 효과는 측정하지 않았습니다.

이 경험을 통해 LLM 분석에서는 모델 선택뿐 아니라 자원 제약, 분류 기준, 출력 형식, 검증 절차를 함께 설계해야 한다는 점을 배웠습니다. 후속 분석에서는 사람 라벨 기반 평가와 프롬프트·모델 비교를 통해 분류의 신뢰성을 확인하고자 합니다.
