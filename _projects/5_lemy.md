## 문제 — 장판 오브젝트가 많아질 때 발생하는 프레임 저하

Lemy는 2D 탑뷰 액션 게임입니다. 몬스터와 장판 오브젝트가 동시에 많이 등장하는 상황에서 프레임 성능이 저하되는 문제가 있었습니다.

기존 장판 처리는 `GameObject`, `Collider2D`, `OnTriggerStay2D`에 의존했습니다. 장판 수가 늘어날수록 물리 트리거와 개별 오브젝트 관리에 드는 비용이 커지는 구조였습니다.

## 접근 — 오브젝트 중심 처리에서 데이터 중심 처리로

- **필요한 상태만 데이터로 관리:** `BurningFieldData` 구조체에 장판의 위치와 지속 시간 등 처리에 필요한 정보를 저장했습니다.
- **충돌 판정 단순화:** 물리 트리거 대신 거리 제곱(`sqrMagnitude`)을 이용해 장판과 대상 사이의 거리를 직접 비교했습니다.
- **시각 효과 처리 분리:** 개별 장판 오브젝트를 사용하는 방식 대신 `ParticleSystem.Emit`으로 시각 효과를 처리했습니다.

이렇게 장판의 게임 로직과 시각 효과를 분리하고, 대량의 장판을 처리할 때 필요한 계산과 상태 관리에 집중하도록 구조를 변경했습니다.

## 결과 — 프로파일링에서 확인한 성능 변화

동일한 테스트 환경에서 구조 변경 전후의 성능을 측정했습니다.

| 측정 항목 | 변경 전 | 변경 후 | 변화 |
|---|---:|---:|---:|
| Physics2D 처리 시간(평균) | 6.41 ms | 2.55 ms | 약 60.2% 감소 |
| 전체 프레임 시간(평균) | 40.02 ms | 31.73 ms | 약 20.7% 감소 |
| GC Alloc(평균) | 34.59 KB | 28.17 KB | 약 18.6% 감소 |

Physics2D 처리 시간뿐 아니라 전체 프레임 시간과 GC Alloc도 감소했습니다. 측정 결과를 통해 이 변경이 물리 처리 비용을 줄였고, 전체 프레임 성능과 메모리 할당 측면에서도 개선과 함께 나타났음을 확인했습니다.

## 나의 기여

팀 프로젝트에서 **기존 장판 처리 구조를 분석하고, 데이터 기반 관리와 직접 거리 판정을 적용했으며, 시각 효과 처리 방식을 변경하고, 프로파일러 수치로 변경 전후를 비교**했습니다.

## 배운 점과 후속 과제

이번 작업을 통해 성능 문제를 오브젝트 수나 물리 엔진의 사용 여부만으로 판단하기보다, 실제 병목을 측정하고 게임 로직에 필요한 계산을 구분해 설계하는 것이 중요하다는 점을 배웠습니다. 또한 물리 트리거를 직접 계산으로 대체하는 방식은 상황에 맞는 충돌 조건과 판정 범위를 신중히 확인해야 하며, 최적화 이후에도 게임 동작이 기존 의도와 일치하는지 검증해야 합니다.

이 페이지는 제가 담당한 기술 작업과 측정 결과를 중심으로 정리했습니다. 프로젝트 소유권과 팀 애셋의 공개 범위를 존중해 이미지와 소스 코드는 포함하지 않았습니다.
