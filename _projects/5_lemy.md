## 문제 — 장판 오브젝트가 많아질 때 발생하는 프레임 저하

Lemy는 2D 탑뷰 액션 게임입니다. 몬스터와 장판 오브젝트가 동시에 많이 등장하는 상황에서 프레임 성능이 저하되는 문제가 있었습니다.

기존 오브젝트 처리는 GC를 줄이기 위해 오브젝트 풀을 사용하고 `GameObject`, `Collider2D`, `OnTriggerStay2D`와 같은 Unity 제공 컴포넌트 및 메서드에 의존했습니다. 짧은 시간에 오브젝트 수가 늘어날수록 풀링을 활용한 GC 제어가 무색해지는 구조였습니다.

## 접근 — 오브젝트 중심 처리에서 데이터 중심 처리로

- **필요한 상태만 데이터로 관리:** 구조체에 오브젝트의 위치와 지속 시간 등 처리에 필요한 정보를 저장했습니다. 기존에는 GameObject 단위로 관리되기 때문에 생성 및 파괴에서 GC 또는 메모리 낭비가 발생할 수 있었으나 구조체는 스택 메모리에 할당된다는 점을 이용해 이를 개선했습니다.
- **충돌 판정 단순화:** 2D Collider 대신 거리 제곱(`sqrMagnitude`)을 이용해 오브젝트와 대상 사이의 거리를 직접 비교했습니다.
- **시각 효과 처리 분리:** 개별 오브젝트를 사용하는 방식 대신 `ParticleSystem.Emit`으로 시각 효과를 처리했습니다. 기존 오브젝트 렌더링 방식과 달리, Particle System은 한 번의 drawCall로 여러 파티클을 동시에 그려내기 때문에 선택했습니다.

이렇게 오브젝트의 게임 로직과 시각 효과를 분리하고, 대량의 오브젝트를 처리할 때 필요한 계산과 상태 관리에 집중하도록 구조를 변경했습니다.

## 결과 — 프로파일링에서 확인한 성능 변화

동일한 테스트 환경에서 구조 변경 전후의 성능을 측정했습니다.

| 측정 항목 | 변경 전 | 변경 후 | 변화 |
|---|---:|---:|---:|
| Physics2D 처리 시간(평균) | 6.41 ms | 2.55 ms | 약 60.2% 감소 |
| 전체 프레임 시간(평균) | 40.02 ms | 31.73 ms | 약 20.7% 감소 |
| GC Alloc(평균) | 34.59 KB | 28.17 KB | 약 18.6% 감소 |

Physics2D 처리 시간뿐 아니라 전체 프레임 시간과 GC Alloc도 감소했습니다. 측정 결과를 통해 이 변경이 물리 처리 비용을 줄였고, 전체 프레임 성능과 메모리 할당 측면에서도 개선과 함께 나타났음을 확인했습니다.

## 나의 기여

팀 프로젝트에서 **기존 오브젝트 대량 생성 구조의 문제점을 분석하고, 데이터 기반 관리와 직접 거리 판정을 적용했으며, 시각 효과 처리 방식을 변경해 렌더링 과정에서도 개선을 이루고, 프로파일러 수치로 변경 전후를 비교**했습니다.

## 배운 점과 후속 과제

이번 작업을 통해 풀링과 같은 표준적으로 쓰던 방법론이 항상 최적화를 보장하지 않는다는 사실과 실제 서비스 구현에서 성능을 고려하는 것이 중요하다는 사실을 깨달았습니다. 또한, OOP는 코드가 깔끔하므로 협업에 유리하다는 장점이 있으나 이 사례의 경우 DOP적 철학과 유니티 내부 기능(물리 연산, 오브젝트 렌더링과 Particle System의 렌더링 차이)에 대한 공부가 최적화 방법론을 구상하는 데에 도움을 주었습니다. 이를 통해 최적화를 할 때 필요한 CS 지식 및 이를 탐색하고 적용하는 법을 배웠습니다.

이 페이지는 제가 담당한 기술 작업과 측정 결과를 중심으로 정리했습니다. 프로젝트 소유권과 팀 애셋의 공개 범위를 고려해 이미지와 소스 코드는 포함하지 않았습니다.
